## Architecture

- [x] [arch-1|high] Flat cost model omits the top-level integration lane (plugins/my-skills/skills/orchestrator/references/config.md:228)
  fingerprint: architecture|plugins/my-skills/skills/orchestrator/references/config.md|flat-cost-model-omits-toplevel-integration-lane
  Rationale: `M_flat` is defined as `max` over lanes of `tasks(L)` plus `A + J +` interface points, and `span_base` for a viable flat verdict as `max` over lanes of `tasks(L)`. Neither adds the top-level integration lane, which `SKILL.md`:1024 dispatches "through a single sequential coder invocation — after all other lanes are DONE, never concurrently with them". The outer model therefore prices a serial lane inside a `max` over concurrent lanes — the exact error ADR-0012 corrected one level down for the integration sub-lane, and the same direction: optimistic. The `Estimated speedup: {T} / {largest lane tasks}` line of the Step 2p.2 flat print block (`SKILL.md`:502) carries the same omission, so the `lanes` figure quoted at the `ask` ladder is understated by `tasks(integration)`. The contradiction is already visible in the source: `SKILL.md`:466 tells the slicing analysis to minimize integration-slice size because `references/config.md` → *The makespan model* "prices as serial" work that cannot be assigned to one slice — a pricing that exists for sub-lanes and does not exist for lanes. arch-1 of the 2026-08-18 backlog is explicitly scoped to the nested sub-lane split and does not reach this; the parent `PACT` has declared an integration-lane region since before that change (`SKILL.md`:814), so the defect predates it.
  Fix: Require the top-level split to declare an `integration` field with the same strict shape and reject-on-omission rule the sub-lane split now uses (`SKILL.md` Step 2p.1), then add `tasks(integration)` to `M_flat` and to the viable-flat `span_base` in `references/config.md` → *The makespan model*, and to the Step 2p.2 flat print block. Exclude the lane from the two work-concentration conditions exactly as the sub-lane integration slice is excluded, and re-verify the worked examples.
  ADR: Price the top-level integration lane as serial in the flat makespan

- [ ] [arch-2|med] span(L) and span_max are the same formula written at three sites (plugins/my-skills/skills/orchestrator/references/config.md:225)
  fingerprint: architecture|plugins/my-skills/skills/orchestrator/references/config.md|span-formula-written-at-three-sites
  Rationale: After ADR-0016, `span(L)` for a split lane reads "`max` over its non-integration sub-lanes plus `tasks(integration)`" and `span_max` for the run reads "`max` over all non-integration lanes of `span(L)` plus `tasks(integration)`" — the same "concurrent max plus serial remainder" shape, stated twice, in two normative prose blocks, at `:225`, `:235` and `:237`. Four sites must move in agreement for any change to integration-lane pricing. The cancellation-identity block ADR-0016 has to *derive* (`span_base = M + X`, `span_max = S + X`, therefore `g = M − S`) exists only because the two are written as separate formulas: under one form `g` is the difference of the same function applied to two slice sets and `X` cancels by construction, with nothing to prove. The same duplication drives three near-verbatim exclusion blockquotes (`:74`, `:482`, `:498`) restating that conditions 1 and 2 skip the integration slice, each with its own worked counter-example, two of them literally repeated — and ADR-0016 §3 has to *assert* "the exclusion applies at both evaluation sites or at neither", which under one rule would be true by construction. ADR-0012 → ADR-0014 → ADR-0016 is one defect found at three depths; a fourth depth costs ADR-0017. Not a correctness defect: the model computes correctly today, and all worked examples reconcile.
  Fix: State one rule over any slice set `P` with declared integration slice `i(P)` — `span(P) = max over non-integration members m of P of span(m) + tasks(i(P))`, with a leaf's `span` = `tasks` and `tasks(none)` = 0 — then derive `span(L)`, `span_max`, and the viable-flat `span_base` as that rule applied to a lane's sub-lane set, the run's lane set, and the run's lane set with every lane unsplit. Collapse the three exclusion blockquotes to one canonical statement plus a one-line pointer at each site. Re-verify every worked example by hand afterwards, since this rewrites the normative text they are checked against. Record as ADR-0017, superseding ADR-0016's derivation framing without changing any figure.
  ADR: One span rule over any slice set, at any depth

## Bugs & Improvements

- [x] [bug-1|med] Report schema forbids the status and summary key the builder always emits (plugins/my-skills/skills/clean-code-gates/schema/report.schema.json:52)
  fingerprint: bugs|plugins/my-skills/skills/clean-code-gates/schema/report.schema.json|report-schema-forbids-emitted-status-and-summary-key
  Rationale: `src/report.cjs:20` puts `gatesErrored` in `summary` on every report, and `:13` can set `status: "error"`, but the schema declares `summary` with `additionalProperties: false`, `required` omitting `gatesErrored`, and `"status": {"enum": ["pass","warn","blocked"]}`. So **every** report already fails its own schema — not only errored ones, because `gatesErrored` is emitted unconditionally — and a consumer running a strict validator in CI would reject all of them. The stale three-value vocabulary is also published as the consumer contract at `SKILL.md`:52 ("`report.summary.status` is `pass | warn | blocked`"), which is the line fixer agents and orchestrators read, so an agent branching on the documented values silently mishandles the `error` case — the "a gate could not execute, so its result is unknown" case that exit code 4 exists to signal. The per-gate `status` enum (`schema/report.schema.json`:100) was updated to include `error` and `skipped`; the summary-level vocabulary was not, so the two halves of one file disagree. This went unnoticed because `__tests__/schema.test.cjs` is a hand-rolled structural validator that checks required keys and types only — it enforces neither `additionalProperties` nor any `enum`, so it passes against a report the real schema rejects. Independent of the exit-code work: FR-5 updated the exit-code documentation it changed and did not touch the status vocabulary.
  Fix: Add `"error"` to the summary `status` enum and `gatesErrored` to `summary.properties` (and to `required`, since it is always emitted), update the `SKILL.md`:52 contract line and any README status list to the four-value vocabulary, and strengthen `__tests__/schema.test.cjs` to enforce `additionalProperties: false` and declared `enum`s so the guard can actually fail — the missing enforcement is why this survived.
  _fixed via orchestrator · df30286 · 2026-08-19_

- [ ] [bug-3|med] Schema validator lost a check it used to have and honours 7 of 10 keywords (plugins/my-skills/skills/clean-code-gates/__tests__/schema.test.cjs:48)
  fingerprint: bugs|plugins/my-skills/skills/clean-code-gates/__tests__/schema.test.cjs|validator-lost-check-and-honours-seven-of-ten-keywords
  Rationale: The generic recursive validator that replaced the hand-rolled one implements `type`, `required`, `additionalProperties`, `properties`, `items`, `enum` and `const` — but `report.schema.json` also uses `minimum` (4 sites), `pattern` (1) and `format` (1), so `blockers: -5`, `gate: "NOTAGATE"` and `line: 0` all validate clean. One of those is a genuine regression rather than a pre-existing gap: the base validator carried an explicit `typeof finding.line !== 'number' || finding.line < 1` check that the rewrite dropped, so `line: 0` was rejected before this change and is accepted now. Exposure is bounded and should not be overstated — the validator is a test fixture, nothing in `src/` validates at runtime, and every finding-construction site in both adapters already floors `line` via `|| 1` or a literal, so no shippable report is affected. What is lost is regression detection, in the guard whose whole purpose is regression detection. The acceptance criteria named exactly the seven keywords implemented, so this is a criteria gap rather than an implementation miss. Note the constraint on the fix: `checkNode` is already at cyclomatic complexity 11 and `checkObject` at nesting depth 3, and the natural fix adds branches to exactly that function.
  Fix: Add `minimum`, `pattern` and `format` to the validator, refactoring `checkNode` in the same change so complexity does not worsen — a keyword-handler table keyed by schema keyword keeps the walk flat. Restore an explicit negative case for `line: 0` so the dropped check is pinned by a test rather than by the implementation. Consider whether the validator belongs in `src/validate-report.cjs` called on the report-writing path instead of in a test fixture, so the defect class becomes unshippable rather than "a fixture might notice" — that is a behaviour change (what does the CLI do when it fails its own schema?) and needs its own decision.
