## Architecture

- [ ] [arch-1|high] Flat cost model omits the top-level integration lane (plugins/my-skills/skills/orchestrator/references/config.md:228)
  fingerprint: architecture|plugins/my-skills/skills/orchestrator/references/config.md|flat-cost-model-omits-toplevel-integration-lane
  Rationale: `M_flat` is defined as `max` over lanes of `tasks(L)` plus `A + J +` interface points, and `span_base` for a viable flat verdict as `max` over lanes of `tasks(L)`. Neither adds the top-level integration lane, which `SKILL.md`:1024 dispatches "through a single sequential coder invocation — after all other lanes are DONE, never concurrently with them". The outer model therefore prices a serial lane inside a `max` over concurrent lanes — the exact error ADR-0012 corrected one level down for the integration sub-lane, and the same direction: optimistic. The `Estimated speedup: {T} / {largest lane tasks}` line of the Step 2p.2 flat print block (`SKILL.md`:502) carries the same omission, so the `lanes` figure quoted at the `ask` ladder is understated by `tasks(integration)`. The contradiction is already visible in the source: `SKILL.md`:466 tells the slicing analysis to minimize integration-slice size because `references/config.md` → *The makespan model* "prices as serial" work that cannot be assigned to one slice — a pricing that exists for sub-lanes and does not exist for lanes. arch-1 of the 2026-08-18 backlog is explicitly scoped to the nested sub-lane split and does not reach this; the parent `PACT` has declared an integration-lane region since before that change (`SKILL.md`:814), so the defect predates it.
  Fix: Require the top-level split to declare an `integration` field with the same strict shape and reject-on-omission rule the sub-lane split now uses (`SKILL.md` Step 2p.1), then add `tasks(integration)` to `M_flat` and to the viable-flat `span_base` in `references/config.md` → *The makespan model*, and to the Step 2p.2 flat print block. Exclude the lane from the two work-concentration conditions exactly as the sub-lane integration slice is excluded, and re-verify the worked examples.
  ADR: Price the top-level integration lane as serial in the flat makespan

## Bugs & Improvements

- [ ] [bug-1|med] Report schema forbids the status and summary key the builder always emits (plugins/my-skills/skills/clean-code-gates/schema/report.schema.json:52)
  fingerprint: bugs|plugins/my-skills/skills/clean-code-gates/schema/report.schema.json|report-schema-forbids-emitted-status-and-summary-key
  Rationale: `src/report.cjs:20` puts `gatesErrored` in `summary` on every report, and `:13` can set `status: "error"`, but the schema declares `summary` with `additionalProperties: false`, `required` omitting `gatesErrored`, and `"status": {"enum": ["pass","warn","blocked"]}`. So **every** report already fails its own schema — not only errored ones, because `gatesErrored` is emitted unconditionally — and a consumer running a strict validator in CI would reject all of them. The stale three-value vocabulary is also published as the consumer contract at `SKILL.md`:52 ("`report.summary.status` is `pass | warn | blocked`"), which is the line fixer agents and orchestrators read, so an agent branching on the documented values silently mishandles the `error` case — the "a gate could not execute, so its result is unknown" case that exit code 4 exists to signal. The per-gate `status` enum (`schema/report.schema.json`:100) was updated to include `error` and `skipped`; the summary-level vocabulary was not, so the two halves of one file disagree. This went unnoticed because `__tests__/schema.test.cjs` is a hand-rolled structural validator that checks required keys and types only — it enforces neither `additionalProperties` nor any `enum`, so it passes against a report the real schema rejects. Independent of the exit-code work: FR-5 updated the exit-code documentation it changed and did not touch the status vocabulary.
  Fix: Add `"error"` to the summary `status` enum and `gatesErrored` to `summary.properties` (and to `required`, since it is always emitted), update the `SKILL.md`:52 contract line and any README status list to the four-value vocabulary, and strengthen `__tests__/schema.test.cjs` to enforce `additionalProperties: false` and declared `enum`s so the guard can actually fail — the missing enforcement is why this survived.

- [ ] [bug-2|med] Prime port never resolves a scan agent, so every digest is gathered inline (prime-agent/skills/orchestrator/SKILL.md:175)
  fingerprint: bugs|prime-agent/skills/orchestrator/SKILL.md|prime-port-never-resolves-a-scan-agent
  Rationale: *The read-only scan subagent type* is carried into the Prime port unrewritten: it resolves `Explore` / `explore` / `general-purpose` / `general` (`:175-177`), and Step 2p.1's call shape still reads `- \`subagent_type\`: the resolved scan type` (`:497`) — the fourth dispatch site, left naming `subagent_type` after the bug-10 overlay renamed the other three to `name`. None of those four types exists under Prime, which dispatches through `rlm(prompt, name=…)`, so resolution always finds nothing and falls through to the documented "never let this resolution fail the run" inline path. The run therefore does not break — it silently degrades: **both** callers, Bootstrap B1's whole-repo context digest and Step 2p.1's slicing analysis, execute in the orchestrator's own context on every Prime run, which is precisely the context cost the scan child exists to avoid, and B1's is a whole-repo read. The gap is already acknowledged in-tree — `prime-agent/overlays/protocol.orchestrator.md`:5 states the scan agent's resolution "is unchanged in this port and is tracked separately" — so this item is that tracking. Adjacent to bug-10 of the 2026-08-18 backlog but outside it: bug-10 is scoped to the parallelism capability gate and its wave dispatch sites, and it left this one deliberately untouched. No security regression — the digest is untrusted input whichever way it is gathered (Step 2p.1), so only *where* the reading happens changes.
  Fix: Add an orchestrator-overlay replacement for *The read-only scan subagent type* that resolves the scan child through `rlm()` under the Prime protocol's read-only-child rule (`protocol.orchestrator.md`:31), and rewrite the Step 2p.1 call shape's `subagent_type` line to the `name`-addressed form the other three dispatch sites now use — anchored per-site at `count: 1`, per the anchor discipline bug-10's fix established. Keep the inline fallback as the genuine no-scan-agent path, and drop the "tracked separately" note from `protocol.orchestrator.md` once it lands.
