The Unreported Delivery

Beck and Orosz argue that what you measure is what you get, and that measuring effort gets you gamed effort. This pipeline measures itself with unusual rigour — and never states what it delivered, what it cost, or which of its gates never ran.

Where the numbers sit on the chain

The article's backbone: effort → output → outcome → impact. Measuring earlier is cheaper, more attributable, and more distorting. Every measurement this framework emits, classified.

Impact at zero is structurally correct, not a defect: the loop has no revenue signal and no user. The defect is that nothing in the framework says so — and that the 58 outcome-adjacent measurements never reach the artifact a human reads.

The analogy, honestly

The article is about human teams inside a hierarchy. Half its argument transfers to an agent pipeline; half of it inverts. Getting this wrong produces confident, wrong advice.

What transfers

  • Goodhart, not BeckOptimising a proxy displaces the goal. The Facebook survey story runs on money and status; an agent has no rating to trade. Cite the mechanism, not the anecdote.
  • Gates are the incentive systemThere is no separate reward channel, so every gate reaches the terminal stage of that story on the day it ships.
  • The metric's own bill is realUber's diff dashboard didn't change lines of code; it changed CI cost. Here a mutation gate priced at 826 mutants is 6.65 hours of compute.
  • Output presented as verdictA green gate suite is a claim about the artifact, never about whether the thing works.

What inverts

  • "Measure less" is unavailableA human team steers through unmeasured channels. Here, every instruction is a measurement or it does not exist.
  • Attribution is trivial; alignment is impossibleEvery role invocation has a cost, a span and a diff. No role has a customer.
  • Spend must be meteredFor agents, cost is not a proxy for value — it is the bill. The agent has no wallet and will not economise unprompted.
  • Reward hacking isn't bad faithAn agent taking the cheapest path is reading the spec literally. The repair is to close the specification, not to change incentives — and unlike a human, it can edit the instrument mid-run.
  • No world-produced eventA deal closing happens independently of the salesperson. Every signal this loop reads is one it generated.

The diagnosis

This framework measures the pipeline, not the software. Of the numbers it emits, the great majority are effort or output. One measurement reaches toward outcome — the tester's e2e on a high-criticality flow — and one reaches toward the commitment — the requirement-coverage map graded by the spec eval. Neither is what the terminal artifact reports. ORCHESTRATOR — pipeline complete prints four cycle counters, a rework ratio and a coverage number. A reader of that banner cannot tell whether the change works, what it cost, or which of the seven gates never ran.

That is the predictable shape of a system built by someone doing forensics on their own runaway runs. Every control exists because a run escaped: max_family_cycles because one spec absorbed 13 reviews across 11 slugs; max_run_minutes because a run reached all three cycle caps and still ran fifteen hours; gate_wall_clock_minutes because a mutation runner spent 43 minutes at 1% CPU. These are better than most engineering organisations achieve — provenance-resolved denominators, loud overrides, calibration data beside every threshold, an explicit refusal to let G8's rework ratio block because the ratio converges as a family worsens and therefore cannot discriminate. But they are all containment metrics. They answer "did this run get out of control", never "did this run deliver what it promised".

Containment worked. Convergence didn't. — the repo's own forensics, on a run that spent every budget it had and shipped anyway

The gap shows at the three handoffs. At the QA boundary, the four-value vocabulary that can honestly say "we did not verify this" collapses to a binary: READY_TO_COMMIT correctly admits MISSING_TOOL and UNMEASURED as non-failures, but the gate table QA fills offers no UNMEASURED cell for G1–G7, and the banner has no field for the unmeasured set. A project with no complexity linter, no mutation runner and no dependency analyser gets a green-looking ship verdict on three gates that never executed. At the PR boundary, the orchestrator's honest miss report — Deferred by decision, Issues found, the eval's recorded-not-remediated gaps — reaches the FINAL and dies there: the story PR body carries Summary, Story, Test plan and Human validation, and nothing else. At the roadmap boundary, READY(r) is legended "the release is shippable" and computes to a count of commit trailers; moving the one laggard to backlog removes it from the matrix and flips the release green.

Underneath all three sits the structural problem: the instrument is inside the tree being measured. .cleancode-gates.json holds every blocking number, is deep-merged user-wins, is auto-written into the repo on first run, and is not among the three keys anchored to the merge-base. The anchor's stated rationale is blast radius — a narrower threat model than the repo's own forensics justify. A branch that sets max_eval_cycles: 0, or adds its own paths to gates.G2.exempt, weakens the measurement of itself from inside the change under review, and no artifact says so. That is the McKinsey dynamic in its agent form: not a person gaming a score, but a system whose cheapest path to a green number runs through the instrument. And the one effort metric the article's argument does not forbid — spend, which for an agent is the actual bill — is the one that ships disabled.

Recommendations

Ranked. Each traces to a principle and to a failure it prevents. S ≈ an hour or two, M ≈ a day. Open one for the design.

R1 Make the terminal artifacts state delivery, cost, and what was not measured MODIFY orchestrator · product-manager SP1 P2 P8 P9 P11

The FINAL banner gains four lines; the PM story PR body gains one section fed from them.

Delivered:   {m} / {t} spec requirements with passing evidence
Not delivered: {requirement} — {deferred | eval-recorded, not remediated} — {follow-up | none}
Unmeasured:  G2 MISSING_TOOL, G6 UNMEASURED (no denominator), G1.branches UNMEASURED
Run cost:    {elapsed} min across {n} boundaries

Delivered comes from the eval evidence matrix over the root plan's ## Requirement Coverage denominator — both already exist. Unmeasured is the set QA already computes. Nothing new is measured; four things already known stop dying at a boundary.

Acceptance
A run on a project with no mutation runner prints a non-empty Unmeasured: line, and its PR body carries the same list. Three deferred requirements appear in Not delivered with follow-up ids, in both places.
Gaming
A clean banner is reachable by deferring less and measuring more — the behaviour wanted. Watch Delivered: it must never be computable from the plan alone, or it becomes a self-graded number.
R2 Anchor the instruments to the merge-base MODIFY orchestrator Step 0b · clean-code-gates MP3 P6 P10

Extend the merge-base rule from "keys that widen blast radius" to "keys that weaken the measurement". Add max_eval_cycles, max_family_cycles, max_qa_cycles, max_review_cycles, gate_wall_clock_minutes, max_spec_requirements to the anchored set, and resolve .cleancode-gates.json thresholds, exempt, exclude and roots from $mb too. Where the two disagree, run on the merge-base value and print one non-suppressible line:

INSTRUMENT MOVED — gates.G2.exempt +3 globs (loosening),
  max_eval_cycles 2 → 0 (loosening) — measured against merge-base values

A loosening move inside the change under review becomes a reviewer finding rather than a silent config read. Legitimate threshold changes still work — they land in their own commit, where the line is informative rather than damning. This unifies two audit proposals into one mechanism and reuses the two-trust-anchors invariant already in PROJECT-CONTEXT.md.

Acceptance
A branch adding "max_eval_cycles": 0 runs with the eval live and prints the moved-instrument line. A branch adding its own files to gates.G1.exempt is measured without the exemption.
Gaming
The escape is to move the instrument in a separate earlier PR — a much higher bar, visible in history, and the same bar a human faces.
R3 Close node-ts G6's fail-open and bound it MODIFY clean-code-gates S/MP3 P5 P9

Two defects, one of them the exact class run.cjs:71-78 exists to forbid.

// node-ts.cjs:547
return { score: denom ? (100 * killed) / denom : 100, undetected, survivors };
//                                              ^^^ empty mutant set → perfect score → pass

A file whose mutants were all excluded, or for which Stryker generated none, scores 100 and passes. It must return the unmeasured state the dart adapter already has. Second: the Stryker spawn at node-ts.cjs:614 carries maxBuffer and no timeout and no killSignal, while the dart runner carries both with a comment naming the 43-minute hang that motivated them. Port gates.G6.budget, the preflight that declines with arithmetic, and the hard timeout — the shared G6 contract already documents all of it; one adapter implements it.

While there: eight of nine adapter spawns carry no timeout, including both whole-suite runs — and config.md:38 claims gate_wall_clock_minutes covers the suite while qa.md:23 forbids it. Fix the doc too.

Acceptance
--gates G6 on a file with zero generated mutants reports UNMEASURED, not pass. A wedged Stryker run returns UNMEASURED (timeout) inside the budget instead of blocking the QA subagent forever.
R4 Generalise the measurement block to every gate and stack MODIFY clean-code-gates · orchestrator/templates/qa.md MP9

The dart G6 result already carries measurement.state ∈ {empty, measured, partial, unmeasured} beside status, so "did it pass" and "was this actually verified" are two fields. Make it universal: every gate result carries it, report.schema.json permits it (today it does not), the run summary carries unmeasuredFiles, and QA's gate table gains the UNMEASURED cell it is elsewhere required to write — today it offers ✅ / ❌ / MISSING_TOOL for G1, G2, G6, G7 and ✅ / ❌ for G4 and G5. The QA progress-log vocabulary needs the same value; today it has an undefined WARN where UNMEASURED belongs.

One special case deserves its own line: dart G4 returns pass when the project enables no naming lints. The tool ran, measured nothing, and is indistinguishable from a clean measurement.

R5 Grade the story's pre-registered Acceptance, not only the derived spec MODIFY product-manager · orchestrator S/MP7 P8

The roadmap story is where a promise is made in advance — ## Acceptance — and it is not what gets graded. PM hands the orchestrator the Brief; the brainstormer writes a spec; the eval grades the spec. The story's acceptance criteria can go unmentioned end to end, and the story is stamped done by the presence of a commit trailer.

Pass ## Acceptance verbatim into the story brief with an instruction that the spec's numbered requirements must cover it; report a per-criterion verdict in the FINAL; stamp done on a trailer plus a FINAL whose acceptance verdicts are all met-or-explicitly-deferred. This is the single most doctrine-aligned change available: it makes the pre-registered commitment the graded unit.

R6 Meter spend unconditionally; aggregate it across the PM queue MODIFY orchestrator · product-manager SP11

max_run_minutes caps; it should not also enable. The run already binds run_started_at unconditionally and mints five timestamped boundaries — compute and print elapsed at each one and in every terminal banner regardless of the cap, and persist it in the FINAL. Default 0 then means "no stop", not "no number".

Same at the PM level: per-story minutes in the progress row, a running sum across the resolved queue, an opt-in max_queue_minutes. A twenty-story milestone where every run is under its 60-minute cap still legally consumes twenty hours, and nothing anywhere can say so. Add a token field where the host exposes it; where it does not, say so in the artifact rather than leaving the field absent.

R7 An outcome observation before READY_TO_COMMIT — disclosure first MODIFY orchestrator/templates/qa.md · tester.md S/MP2 P7

For each critical flow the diff touches, QA records whether the built thing was executed through the user-visible path it was changed for: the verbatim command, its exit code, and the behaviour observed. Where it was not executed, that non-observation and its reason go into the QA report, the banner and the PR body.

Keep it a disclosure, not a blocker, in the first iteration. A hard gate on "did you run it" is satisfiable by --version; a required disclosure a human reads is not. Promote it to blocking once a few runs show what honest observations look like — the same discipline config.md:36 already applies to max_run_minutes. This is also the honest place to write the framework's ceiling: a closed loop can observe execution, never outcome. The report should say which is which.

R8 Delete the false "green tree" warrant MODIFY orchestrator/SKILL.md:931 SP7

The scope-band refusal tells the operator to split on phase boundaries "because each phase is already required to exit on a green tree and is therefore already a shippable unit". The actual rule is "EVERY applicable command was run and its verdict recorded — exit 0, or a carried GATE entry" (architect.md:146), and coder.md:177 says in terms that a gate finding is not a stop: record what you cannot clear and proceed. A phase can exit red, by design and for good reasons.

Attribute verification to the boundary that performs it — the run's tester/reviewer/QA barriers — and give each proposed split group a needs: token naming what it depends on. One paragraph of text; it is on the list because a false warrant inside a refusal banner is exactly the kind of claim that gets believed.

R9 READY means landed MODIFY roadmap MP1 P4 P7

READY(r) is a count of trailer commits found by git log --grep on any branch, legended "the release is shippable", and a story moved to backlog leaves the matrix entirely — so parking the laggard flips the release green. Make done require the story's commit to be an ancestor of a declared integration ref, and render a non-suppressible departure list: stories that carried the release band and left it without landing. Keep the trailer as the identity mechanism; change the predicate from "a commit exists" to "the code reached the trunk".

R10 A retry reuses the SPEC id MODIFY product-manager SP10

The family budget is the only cross-run cost control, and it resolves from spec provenance. PM invokes the orchestrator with story brief prose; a re-run after a STALLED story re-types the brief, mints a fresh SPEC-*, and starts the family at zero — the documented cascade vector, reproduced by the framework's own retry path. PM already logs per story; log the SPEC-* id too and pass it positionally on any retry of the same story.

R11 A deferral needs a correction MODIFY orchestrator/templates/architect.md + reviewer/eval SP8

Deferred is written by the architect, exempts the requirement from structural completeness and from the grade, and its follow-up field legally reads none yet. The article's accountability unit is "I take accountability for the miss, here is the cause, here is the change." Require every deferred row to carry a follow-up id or an explicit accepted — {reason}, and surface the deferral count where someone reads it (R1).

Two new skills

Only two gaps genuinely cannot live inside an existing skill. Both sit at the boundary where the closed loop has to open.

/uat

description: Walks a human through the pending validation spots the
  pipeline recorded, captures pass/fail with evidence, stamps the
  stories, and writes the failures as a validation file
  /validation-fixer can consume.

The producer exists and the consumer does not. PM appends to /roadmap/human-validation-queue.md — an append-only file that accumulates flagged spots while "the operator works the queue" by hand — and in conservative mode halts asking for exactly this. Meanwhile validation-fixer consumes a hand-written markdown file of bullets.

/uat is the missing middle: read the queue and the story's Acceptance, present each check with its PR URL, record the human's verdict and evidence, stamp passes into the story's audit log, write failures in validation-fixer's own input shape, hand off. It is the only place a signal the pipeline did not generate can enter — which is precisely the article's point about sales: outcome is measurable because the world, not the worker, produces the event.

/delivery-ledger

description: Read-only. Aggregates every FINAL report, QA report and
  PM log into one append-only delivery ledger — per run: requirements
  committed, delivered, deferred, gates unmeasured, validations
  outstanding, and cost — and renders the trend.

Nothing owns the cross-run view. The orchestrator is per-run, roadmap is doc-only planning, PM is per-story, pr-review-report is per-branch. So the question the article ends on — deliver the impact committed to — has no artifact here at all, and the question the repo's own forensics keeps asking (what did that family cost, how much was rework) is answerable only by hand-reading .progress.md files.

It writes no gate and blocks nothing, and the skill text should say so: this is the diagnostic tier, and promoting any of its numbers to a gate is a deliberate, reviewed change. Its rows are R1's four lines plus provenance — which is why R1 comes first. The ledger is cheap once runs state their own delivery, and impossible before.

What not to do

Don't build a pipeline-metrics dashboard

Cycle counts, tokens per role, diffs per run, gate-pass rates over time: all effort, all cheap, all optimisable by an agent that reads them. This is the Uber CI-cost anecdote waiting to happen — the metric didn't change the code, it changed the bill. The ledger reports delivery and cost per run; it must not rank roles.

Don't gate on G8

The rework ratio is already correctly advisory, with the argument attached: it converges as a family worsens, so it cannot discriminate — the eight-hour cascade scores 0.67. That analysis is better than the metric that would replace it.

Don't make R7 blocking on day one

A hard "did you execute it" gate is satisfiable by the cheapest possible execution, and the agent has no way to know that is not what was wanted. Disclosure first, blocking later, with runs to calibrate against.

Counting Stryker's Timeout as killed is not a defect

A correction to one audit finding. Stryker's own mutation score counts timeouts as detected — a mutant that sends the suite into an infinite loop was caught by it. mutation_test's timeouts mean the opposite, which is why dart routes them to G6_UNRUN. The adapters correctly follow different tools' semantics; document the divergence in the shared G6 contract so the next reader does not "fix" one into the other.

Don't add a token-cost cap before a baseline

config.md:36 already makes this argument for max_run_minutes and it is right: a number chosen badly stops good runs. Report first, cap once the distribution is known.

Don't build a metric-registry skill

The registry P6 asks for is a table in orchestrator/references/config.md listing every number, its chain position, and whether it blocks — a reference doc with a linter, not a skill.

Don't try to measure impact inside the loop

The pipeline has no revenue signal and no user; anything claiming to measure impact internally is measuring something else. P8 is a handoff obligation, not a gate.

Verdict

Would following these make the framework more efficient? Mostly no — and that is the answer, not an evasion.

Efficiency means cost per run, and four items touch it: R3 (a wedged mutation runner blocks a QA subagent indefinitely), R10 (a retry unbinds the only cross-run budget), R2 (a false green ships a defect that costs a whole later family), R6 (nothing can be stopped that is not measured). R8 is negative cost — it deletes a false sentence. Everything else adds work: runs get slower and reds go up. If the success metric is "pipeline complete", these make the framework look worse. That is the point. A system optimises what it can measure; this one measures completion, so it completes.

R4 and R7 are likeliest to pay for themselves in clarity and least likely to pay for themselves in tokens.

And the honest bottom line: this question is unanswerable today, because the framework cannot state what a run cost or delivered. Ship R6 and R1, run a milestone, and it is answerable from the project's own numbers instead of anyone's opinion — the doctrine applied to the doctrine.
