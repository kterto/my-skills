Section one

Your three theories, graded

Each was tested head-on against the artifacts, then attacked by two independent adversarial verifiers before anything was allowed to stand.

Confirmed · dominant

Rules the roles don't share

Not mutual contradiction so much as a lossy contract chain. The reviewer gates on the plan's acceptance criteria; spec-driven-eval gates on the spec; the gate thresholds fork four ways between architect, coder, tester and QA. Every fork is a manufactured cycle.

Decisive: one diff, three verdicts — tester PASS at 71.41%, reviewer blocking MF-5 for the same tests, QA ❌ at ≥85%.

Partial · wrong mechanism

The skill is too large

The size is real and extreme, but agents are not losing the thread inside a long file — the sequential core the pipeline actually runs is only 13% of SKILL.md. What size actually costs is a fixed token tax and, measurably, silently skipped mandatory steps.

Decisive: 55.6% of SKILL.md governs a parallel path that has produced 0 PACT artifacts in lotery_oracle — and the mandatory simplify pass logged 0 entries on the run that then burned 4 cycles on complexity.

Refuted

toodls grew too big

The worst run in the corpus happened in the smaller, younger project. toodls' reviews-per-feature is flat or improving straight through the window you report degradation in. Within toodls, correlation between plan size and rejections is 0.04.

Decisive: 2026-08-20 — lotery_oracle 8.0 CR per spec; toodls 3.3 for the same half-month, against a larger context and a longer history.

Section five

The fix, in order

Ordered by impact over effort. Items 1–5 close contract gaps and are where the cycles come back; items 6–8 are volume and hygiene. Doing 6 first would feel productive and move nothing.

P1Give the plan a per-requirement coverage map, and bind the reviewer to itM~33%

Add a mandatory ## Requirement Coverage table to the plan template, immediately above ## Acceptance Criteria: one row per numbered spec requirement — spec FR # · covered by AC # · Met-by-plan / Deferred + reason + follow-up id. An unmapped requirement is a BLOCKED stop, not an omission. Then rewrite the reviewer's first evaluation bullet to gate on the map, and pass spec_path in the reviewer dispatch so it can resolve it. Scope the reviewer to the map, not to a free re-read of the spec, so review cost doesn't balloon.
